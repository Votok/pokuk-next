# Azure runtimes for the Next.js gallery

Research for [issue #4](https://github.com/Votok/pokuk-next/issues/4), 22 November 2026.

Azure App Service on Linux and Azure Container Apps Consumption can both run a full Next.js server. On either, a visitor can open an event, a Server Component can fetch its manifest from Blob Storage on the server, and the browser can hydrate the lightbox to handle keyboard input. A future Server Action can receive a POST on that same runtime. This is a compatibility finding from the providers’ documentation. Startup latency, image workload and rollout behavior still need measurement with synthetic fixtures. [Next.js deployment support](https://nextjs.org/docs/app/getting-started/deploying) · [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components) · [Server Action security](https://nextjs.org/docs/app/guides/data-security)

| Decision factor | App Service for Linux, Basic B1 | Container Apps, Consumption |
| --- | --- | --- |
| Deployment | Build for a supported Node.js version, ship dependencies and run the production Next.js server on the assigned port. Basic supports up to three instances with manual scaling. Staging slots begin at Standard, so a B1 rollout needs another rollback method, such as redeploying a retained build. [Node.js configuration](https://learn.microsoft.com/en-us/azure/app-service/configure-language-nodejs) · [Tier limits](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/azure-subscription-service-limits#azure-app-service-limits) | Build a Linux amd64 image and provide a registry the service can pull from. Revisions allow traffic to move between retained builds. Consumption has fixed CPU/memory pairs, so size and test the image-processing workload together with the web server. [Containers](https://learn.microsoft.com/en-us/azure/container-apps/containers) · [Revisions](https://learn.microsoft.com/en-us/azure/container-apps/revisions) |

Deployments and restarts still need warm-up. Minimum one keeps capacity available and adds idle or active charges. Traffic distribution and time spent alive between bursts affect the bill. **Static export boundary.** A static export executes Server Components at build time and can hydrate the lightbox. Published manifest changes then need a rebuild to affect those rendered pages. The static host cannot perform a per-request server-side Blob read, receive a Server Action, perform incremental static regeneration (ISR) or use the default Next.js image optimizer. Azure Static Web Apps also offers a distinct hybrid Next.js preview with a server backend. Microsoft lists a 250 MB app limit, unsupported linked APIs and an image-caching limitation under ISR. [Next.js static exports](https://nextjs.org/docs/app/guides/static-exports) · [Azure Static Web Apps Next.js support](https://learn.microsoft.com/en-us/azure/static-web-apps/nextjs)

## Data access, freshness and photographs

- Both Azure services expose a managed identity. The server can use that identity with the Azure SDK and a container-scoped Storage Blob Data Reader role. Keep credentials and private manifest fields server-side. A future mutation needs its own authorization check inside the action and a narrowly scoped grant for any write it performs. [App Service identity](https://learn.microsoft.com/en-us/azure/app-service/overview-managed-identity) · [Container Apps identity](https://learn.microsoft.com/en-us/azure/container-apps/managed-identity) · [Blob RBAC](https://learn.microsoft.com/en-us/azure/storage/blobs/authorize-access-azure-active-directory) · [Next.js data security](https://nextjs.org/docs/app/guides/data-security)
- Decide how soon visitors must see a published manifest. Request-time reads can fetch it afresh. An explicitly cached result needs a freshness period or publication-triggered invalidation. Self-hosted Next.js caches default to each instance’s memory and filesystem. Replica-local storage vanishes on replacement in Container Apps. Multiple instances or revisions can serve different cached generations unless they share and coordinate invalidations. Reuse the same Next.js build across replicas, coordinate the Server Action encryption key across instances, and test stale clients during rollout. [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting) · [Container Apps storage lifetimes](https://learn.microsoft.com/en-us/azure/container-apps/storage-mounts)
- Browsers can fetch published image variants directly from Blob Storage when the media access policy permits it. This avoids sending each image through the web process. The alternative of self-hosted Next.js image optimization generates variants on demand and uses cache space and CPU. Restrict allowed remote origins and paths. Its default optimizer omits authentication headers on upstream fetches. For private photos, a server-authorized media response or a short-lived scoped user-delegation SAS requires an explicit access and cache policy. Keep personalized responses and bearer URLs out of shared public caches. [Blob delivery](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-blobs-introduction) · [Next.js Image](https://nextjs.org/docs/app/api-reference/components/image) · [User delegation SAS](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-blob-user-delegation-sas-create-javascript) · [Next.js cache controls](https://nextjs.org/docs/app/guides/self-hosting)

## Low-traffic worked estimate

**West Europe, public USD pay-as-you-go rates checked 22 November 2026.** The invented month assumes 730 hosting hours, 20,000 external app requests, 20 GB-month of existing hot locally redundant (LRS) block blobs, 10,000 billed Blob read operations across manifest and direct media delivery, and 10 GB total internet egress. Assume co-located services, remaining monthly free allowances, default Azure networking, an existing registry with zero incremental cost and zero chargeable log ingestion. The model excludes tax, domains, custom networking, separately paid registry, CDN, paid monitoring and gallery writes. Existing storage capacity is shown once in each total. [Azure retail catalog](https://learn.microsoft.com/en-us/rest/api/cost-management/retail-prices/azure-retail-prices) · [Bandwidth](https://azure.microsoft.com/en-us/pricing/details/bandwidth/) · [Container Apps networking charges](https://learn.microsoft.com/en-us/azure/container-apps/custom-virtual-networks) · [Monitor pricing](https://azure.microsoft.com/en-us/pricing/details/monitor/)

For Container Apps, assume minimum zero, 0.5 vCPU and 1 GiB per replica, and **20 aggregate running replica-hours** over the month, including startup and scale-down time. This gives 36,000 vCPU-seconds, 72,000 GiB-seconds and 20,000 requests. The subscription grants 180,000 vCPU-seconds, 360,000 GiB-seconds and two million requests per calendar month. If other apps exhaust all three grants, those same active meters add 36,000 × $0.000034 + 72,000 × $0.000004 + 0.02 × $0.56 = $1.5232, bringing the example to **$1.92** while the bandwidth allowance remains available. If egress grows to 200 GB, the extra 100 GB on Europe’s standard Microsoft network route adds **$8.70** to either example. The maintainer’s decision turns on the acceptable first-visit delay after inactivity, the required manifest freshness, whether the web process transforms images, and whether a predictable monthly instance charge is worth keeping the app warm.
